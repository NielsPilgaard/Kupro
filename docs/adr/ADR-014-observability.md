# ADR-014: Observability — self-hosted Grafana stack

## TL;DR

- API + migrations export OTLP to Grafana Alloy, which fans out to Loki (logs), Tempo (traces) and Prometheus (metrics), and scrapes host, Postgres and Keycloak metrics; Grafana OSS on top. Same containers locally (`aspire run`) and in prod (`aspire publish`).
- One request log line per request: method, path, route template, caller kind (session/token/agent/anonymous), status, duration. No query strings, headers, bodies, emails or names.
- Datasources, dashboards (health, usage, errors) and alert rules are provisioned from files in `infrastructure/observability/` — see its [README](../../infrastructure/observability/README.md).
- ~1 GB RAM steady, hard limits sum to ~2.8 GB; 30-day retention. Alerts by email; PingPuffin (DK) checks from outside that the host is up.

## Status

**Accepted**

## Context

The latency budget ([ADR-010](ADR-010-performance-budget.md)) needs production percentiles and an alert, a solo
operator needs to hear about errors before users do, and agent parity ([ADR-001](ADR-001-agent-parity.md)) is only
visible if traffic is split by caller. Skoleoverblikket does this with Grafana Cloud, but Grafana Labs is a US company
and telemetry carries route templates, timings and error text — keeping it on our own EU host is the
[ADR-006](ADR-006-eu-vendor-policy.md) answer. Aspire's dashboard ([ADR-012](ADR-012-aspire.md)) is in-memory only and
has no alerting.

## Decision

- **Signals**: ServiceDefaults configures OpenTelemetry for all services with `service.namespace=flowstate`,
  `deployment.environment.name` and `service.version`; `service.name` is the Aspire resource name (`api`,
  `migrations`). Traces include EF Core/Npgsql (SQL spans) and record exceptions; metrics include ASP.NET Core,
  Kestrel, runtime, HttpClient, EF Core and the Npgsql pool.
- **Pipeline**: apps → Alloy (OTLP http) → Loki `/otlp`, Prometheus OTLP receiver, Tempo. Apps only know the
  collector, so the backends can change without touching app config. Under `aspire run` Alloy also forwards
  everything to the Aspire dashboard, so both views work locally.
- **Collector = Grafana Alloy** (OSS, Apache-2.0), not the upstream OpenTelemetry Collector: same OTLP components,
  plus built-in host (node), Postgres and Prometheus-scrape support, so the host's disk/memory, Postgres and Keycloak
  are watched without extra exporter containers. Scraped metrics are remote-written to Prometheus. Usage reporting off.
- **Config as code**: Grafana is provisioned from files (datasources with fixed uids `prometheus`/`loki`/`tempo`,
  dashboards, alert rules, email contact point). Dashboards and rules are generated by `build_dashboards.py` and
  read-only in the UI; CI fails on drift.
- **Request log**: ASP.NET Core HttpLogging, combined into one line, with a `Route` and `Caller` field added by an
  interceptor (`Common/RequestLogging.cs`). Dashboards aggregate these lines in Loki rather than the HTTP metrics:
  at low traffic counter series are born with their final value and `rate()` undercounts (seen in Skoleoverblikket).
  Health probes are not logged.
- **Budget**: latency numbers use *warm* requests (reused connection) so a deploy's cold-start burst doesn't count;
  percentiles are hidden below a minimum sample size.
- **Alerts**: API down (no health probe for 5 min), errors logged, restart loop, p99 over budget — email via the
  Scaleway TEM SMTP relay. Grafana evaluates them, so they die with the host; PingPuffin covers that case.
- **Privacy**: telemetry is operational data. Only internal ids and route templates; query strings carry tokens and
  are never logged. Caller kind, not user id or token name. Grafana, Loki and Tempo usage reporting is off.

## Consequences

### Positive

- **POS-001**: No telemetry leaves the VPS; nothing to add to the sub-processor list for observability.
- **POS-002**: ADR-010's production half (p50/p99 per endpoint, budget alert) is in place before the first feature.
- **POS-003**: Monitoring config is code: reviewed, regenerated, drift-checked in CI, and identical in dev and prod —
  a dashboard can be built and checked against local traffic.
- **POS-004**: Vendor-neutral instrumentation: switching backend = changing the collector's exporters.
- **POS-005**: One container covers app telemetry and infrastructure metrics (disk full, Postgres/Keycloak down alerts).

### Negative

- **NEG-001**: ~1 GB RAM steady (limits: Loki 768m, Tempo 768m, Prometheus 512m, Grafana 384m, Alloy 384m) and
  five more containers to upgrade on the single VPS ([ADR-004](ADR-004-hosting.md)).
- **NEG-002**: Monitoring shares the host it watches: a dead VPS can't alert. Mitigated by the external uptime check.
- **NEG-003**: Dashboards depend on log field names; renaming one blanks panels (guarded by `RequestLoggingTests`).
- **NEG-004**: Telemetry is lost with the volumes; it's not backed up (30 days of operational data, acceptable).
- **NEG-005**: Alloy's config is its own language (`.alloy`), not the OTel Collector YAML most examples use.

## Alternatives Considered

### Grafana Cloud (EU region)

- **ALT-001**: **Description**: OTLP straight to Grafana Cloud's gateway, as Skoleoverblikket does. No infrastructure to run.
- **ALT-002**: **Rejection Reason**: US vendor in the data path ([ADR-006](ADR-006-eu-vendor-policy.md)), even with EU-region storage.

### `grafana/otel-lgtm` all-in-one image

- **ALT-003**: **Rejection Reason**: Meant for dev/demo; one container hides per-component limits, retention and upgrades.

### Upstream OpenTelemetry Collector (contrib)

- **ALT-005**: **Description**: The first implementation; standard OTel YAML config.
- **ALT-006**: **Rejection Reason**: Host, Postgres and Keycloak metrics would need extra exporter containers or
  receivers to configure by hand; Alloy ships them and has a pipeline UI for debugging.

### Aspire dashboard in production

- **ALT-004**: **Rejection Reason**: In-memory only, no alerting, no retention; was an exposed port in the generated compose.

## Implementation Notes

- **IMP-001**: Topology in `src/Flowstate.AppHost/Observability.cs`; component config in `infrastructure/observability/`. Locally Grafana is on <http://localhost:3180> with anonymous admin.
- **IMP-002**: Production variables, Grafana domain and PingPuffin setup: [deploy runbook](../runbooks/deploy.md).
- **IMP-003**: The compose healthcheck probes `/alive` (`/health` under `aspire run`); the "API down" alert relies on it.
- **IMP-004**: One-shot runs (`migrate`) must call `FlushTelemetry()` before exiting, or their logs are lost.
- **IMP-005**: CI stamps `service.version` with the commit (`-p:SourceRevisionId=<sha> -p:IncludeSourceRevisionInInformationalVersion=true`; the second is off in `Directory.Build.props`) when images are built ([task 013](../../tasks/013-deploy.md)).
- **IMP-006**: Agents query Grafana through `mcp-grafana` (`.mcp.json`, read-only); Tempo's MCP server is enabled so trace tools work.
- **IMP-007**: Not yet covered: browser errors/web vitals (Grafana Faro), container logs other than the apps' (needs the Docker socket), Keycloak traces.
